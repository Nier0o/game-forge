## 6.4 Limitations and Known Issues

Game Forge is a working end-to-end system, but several deliberate scoping decisions and known constraints shape what it can and cannot produce. This section documents them honestly, grouped by subsystem. The recurring design theme is a preference for guaranteed playable output over open-ended flexibility: wherever the system had to choose, it constrains generation to a verified set of parts rather than risk producing a broken game.

### 6.4.1 Game Scope and Design Generation

#### Only Three Game Archetypes

The planner supports exactly three archetypes — platformer, top-down, and endless-runner. Any prompt describing a genre outside these three (RPG, puzzle, tower-defense, racing, fighting, and so on) is force-fit into the nearest supported archetype rather than rejected. This is a deliberate scoping decision that keeps every generated game within a verified template family. The pipeline is structured to extend later — the asset service already carries perspective presets for additional archetypes — but as it stands the genre coverage is narrow.

#### Archetype Misclassification

The archetype is chosen by a separate zero-shot LLM classifier that defaults to platformer whenever the prompt is ambiguous. As a result an "endless runner" or "dungeon crawler" prompt can occasionally be built as a platformer, silently changing the kind of game the user asked for. The classifier runs at temperature 0 with a substring-match fallback to reduce this, and a stronger archetype hint in the system prompt is the targeted fix.

#### Fixed Behavior and Weapon Catalog

Enemy behaviors, player weapons, and win conditions are all drawn from a fixed catalog defined per archetype. A behavior the plan references but that is not in the catalog is silently dropped; weapons are limited to melee and ranged; and an unsupported win condition is coerced to a safe per-archetype default. This means novel or emergent mechanics a user describes cannot be realized — the game is limited to combinations of pre-written, Godot-verified parts. Optional LLM-authored custom-behavior and script-override channels exist for advanced cases, but they are validated and dropped if malformed, so they can never break a build.

#### Generic Fallback Plan

If the language model fails to return a usable plan after two attempts, the planner falls back to a generic hard-coded default plan, retaining the user's prompt only as a short description string. In that situation the user can receive a generic game bearing little relation to their request. The fallback is a last resort that guarantees the pipeline always returns something buildable rather than erroring out entirely.

#### Fragile JSON Dependency and Latency

Plan generation depends on the model returning parseable JSON, recovered through custom comment-stripping and extraction heuristics, with the generation call capped at 16,000 tokens; very large or malformed plans can be truncated and force the fallback. Planner latency is also high and highly variable because it relies on a shared third-party inference provider, making end-to-end time unpredictable — from tens of seconds to minutes — and outside the system's direct control. Response caching or a self-hosted model would reduce this variance.

### 6.4.2 Visual and Audio Asset Generation

#### Asset Generation Is the Pipeline Bottleneck

Image and audio calls to Stability AI are issued sequentially — one image per entity plus terrain tiles, a background, and a music track — so total asset time scales linearly with the number of entities and dominates the end-to-end latency of a generation. Code assembly, by contrast, runs in parallel and is effectively free. Batching and caching of asset calls are the identified optimizations for reducing overall generation time.

#### Dependence on External Image Credits

Asset generation requires a valid Stability AI key with available quota. When the key is missing or the quota is exhausted, per-asset generation fails and the game falls back to bundled placeholder sprites — a silent visual downgrade. A configuration flag allows the stack to run in a static-asset mode entirely without image credits for testing and demonstration.

#### No Frame-by-Frame Sprite Animation

The asset pipeline produces a single still image per entity rather than a spritesheet. All in-game motion is animated procedurally in Godot at runtime, and transparent cutouts rely on the provider's background-removal step over a solid-color prompt. This is intentional — it avoids the cost and unreliability of true multi-frame generation — but it means generated games cannot display genuine frame-by-frame character animation, and an imperfect cutout can occasionally leave a halo or clip the subject.

#### Art Style Is Not Always Exact

The requested art style is not always honored precisely. Some style labels are remapped — for example "hand-drawn" is served through a full-color comic-book preset and monochrome line-art is avoided — so the delivered look can differ from the label the user chose. These substitutions are deliberate and are made to keep output full-color and visually usable.

#### Sound Effects Are Library-Matched, Not Generated

Only the background music (and an optional boss track) is AI-generated; sound effects are selected from a small fixed library of royalty-free clips by keyword matching against the plan's sound events. An event whose name matches no keyword falls back to a generic interface click, so SFX variety is limited and may be a weak thematic fit for uncommon game concepts. The trade-off guarantees every event has a clean, correctly-timed sound at no generation cost.

#### No Asset Caching

There is no caching or reuse of generated assets — identical prompts regenerate from scratch on every run, wasting API credits and time on re-rolls and on similar games. Caching by visual description is identified as future work.

### 6.4.3 Code Assembly

#### Template-Bounded Generation

The code service performs no LLM code generation; it assembles pre-written, Godot-verified GDScript fragments selected by the plan. This is the system's core reliability guarantee — assembled projects almost always compile and run — but it also means the universe of possible games is bounded by the archetype libraries. Anything that cannot be expressed through the catalog's behaviors, weapons, and hooks cannot be built.

#### Validation May Be Skipped

Assembled projects are checked with the Godot CLI before upload, but when the Godot binary is unavailable in the container that check is skipped. In that mode malformed authored GDScript could reach the builder unchecked. Because the built-in library fragments are pre-verified, the residual risk is confined to the optional authored channels.

#### The Repair Loop Degrades Rather Than Repairs

When validation fails, the retry loop strips the offending file's authored extras and re-assembles; after the retry cap it proceeds despite the failure. This keeps the build alive but does so by silently removing authored content, so the final game can be simpler than the plan described. Built-in behaviors are never the cause of such a failure, so the core game is preserved.

#### Bounded Level Variety

Level layouts are generated procedurally from a limited set of section, room, and pattern templates driven by a seeded random generator. Variety is real but bounded by the template library, so layouts can begin to feel repetitive across many generations. A stored seed makes each run reproducible while keeping successive generations different.

### 6.4.4 Build and Export

#### Environment-Sensitive Godot Export

Full HTML5 export is sensitive to the environment and pinned to a specific Godot CLI version, and it is retried only once before failing. A toolchain mismatch or a transient export error can therefore fail the entire build. A skip-export stub mode is provided so the rest of the orchestration can be exercised without a real Godot export.

#### WebAssembly Delivery Constraints

The output is a WebAssembly HTML5 bundle that requires a modern, cross-origin-isolated browser, and the playback bundle exceeds the recommended size advisory. Older browsers and low-end or mobile devices may run the exported game poorly, and on-device performance has not been formally profiled. Web export is nonetheless the intended delivery target, with performance tuning deferred to post-deployment.

### 6.4.5 Orchestration, Scale, and Reliability

#### No Queue or Concurrency Control

Generation is fire-and-forget, running one background job per request with no queue, concurrency control, or rate limiting. Under concurrent use, every request hits the language and image providers simultaneously with no backpressure, and the system has not been load-tested. This is acceptable for a single-user or demonstration deployment; a work queue is the identified next step for multi-user scale.

#### No Partial Recovery or Cancellation

Any stage failure fails the whole generation and discards partial artifacts, so a late-stage error throws away an already-successful plan and its assets. Users also cannot cancel an in-flight build. Failure states are marked cleanly and surfaced to the interface.

#### Polling-Based Progress and Best-Effort Status

Build progress is delivered by client polling with exponential backoff rather than a live stream, so updates lag by the poll interval and there is no live log feed. In addition, the cross-record status updates between the job, build, and project documents are best-effort and swallow errors, so their status can briefly drift out of sync if an update call fails. Both are simple, robust choices whose terminal states converge in the common path.

### 6.4.6 Authentication and Security

#### Token Stored in Browser Storage

The authentication token is stored in the browser's local storage rather than an httpOnly cookie, which leaves it exposed to theft via cross-site scripting. This is a known trade-off of the single-page-application authentication flow.

#### Shared Inter-Service Secret

Services authenticate one another with a single shared static secret, and an empty secret disables that check entirely — the development default. There is no per-service identity or mutual TLS, so a leaked secret would authenticate as any service. This is adequate inside a trusted internal network, and the production configuration refuses to start with the secret unset.

#### Publicly Addressable Game Files

Generated game files are served publicly by game ID with no ownership check (downloads are verified only when a user session is present), so anyone who knows or guesses a game's URL can play it. The game ID is a random UUID that is unguessable in practice, and public playback is desirable for sharing.

#### Unsanitized Prompt Input

The user's prompt is passed to the design and art language models largely unsanitized, which leaves room for prompt-injection. The downstream impact is bounded, however, because all model output is schema-validated and any behavior or weapon not in the catalog is dropped before it can reach the game.
